# kmp-aria

React Aria's component set rebuilt in **Compose Multiplatform for Web** (Kotlin/Wasm, canvas
render path), measured component by component. The question: *what can Compose Multiplatform
for Web actually do on the browser, and what of it reaches assistive technology?*

React Aria is the yardstick because it is the accessibility reference implementation of the
web (WAI-ARIA patterns, keyboard interaction, focus management) and it is unstyled, so the
port is judged on behaviour and the accessibility tree, not on looks.

This is **not a wager that the canvas path passes.** The Compose web accessibility layer
mirrors only eleven semantics properties into its DOM overlay (brains vault note
`kmp-web-accessibility`, verified 2026-08-31): stateful widgets lose `aria-checked`,
`aria-pressed`, `aria-expanded`, `aria-selected`, `aria-valuenow`, `aria-live`, `tabindex`.
Per-component failure documentation, with mechanism, is a stated goal. The other deliverable
is developer-experience findings, "what fought back", that only come from building this much
behaviour in Compose on the web.

## Decision record (2026-09-02)

| Option | Verdict |
|---|---|
| Plain DOM via kotlinx-browser (js + wasmJs) | Rejected by oxzo (would have been the recommended path for ARIA parity) |
| Compose HTML (Kotlin/JS only) | Rejected: JS-only, "an exploration, not a commitment" (JetBrains blog, Aug 2026) |
| Kilua (Compose runtime to DOM) | Rejected: unvetted framework between Kotlin and the DOM |
| **Compose Multiplatform canvas, wasmJs** | **Chosen.** JetBrains' headline web path. |

Fidelity target: **behaviour and accessibility-contract parity**, not API-shape parity. The
Kotlin API is idiomatic Compose; render props and slots become `@Composable` lambdas.

Targets: `wasmJs` is the measured surface. `jvm` exists only for fast inner-loop tests. No
`js()`, no Android, no desktop app.

## Layout

```
stately/      commonMain, pure Kotlin state (= react-stately). jvm + wasmJs.
aria/         Compose behaviours + semantics (= react-aria hooks). Modifier-level
              press/keyboard/focus, FocusScope, labelling, per-component semantics.
components/   assembled unstyled components (= react-aria-components) + the demo app:
              one hash route per component, plus Material3 control routes (#/m3-<widget>).
conformance/  Node: Vite+React reference app (react-aria-components 1.21.0, same routes),
              Playwright specs, report generator. Writes CONFORMANCE.md.
tools/        bundle-size.sh, loc.sh, inner-loop.sh (scripted metrics)
PREDICTION.md pre-registration, committed before the first source commit
NOTES.md      "what fought back", written the same day
CONFORMANCE.md the per-component table, generated by script; a hand-edited row is a bug
```

## Two instruments per component

1. **Semantics-tree instrument**: Compose UI tests (`runComposeUiTest`) asserting the
   react-aria keyboard/pointer contract against Compose's own semantics tree. Answers *did the
   port implement the behaviour?* Runs on JVM for speed and on wasmJs for truth. A JVM-only
   pass is recorded as a substitution, not a pass.
2. **Browser-a11y-tree instrument**: Playwright runs the same interaction script against three
   URLs (React Aria reference, Compose port, Material3 control) and captures `ariaSnapshot()`
   after each step. Answers *what did assistive technology receive?* The Material3 column
   separates *port bug* from *framework ceiling*.
3. **Manual Orca pass**, one component per tier, quarantined in NOTES.md. Where Orca and the
   framework source grep disagree, the grep wins.

Harness proof before any result counts: the reference passes its own goldens and a
deliberately broken port ToggleButton (no `toggleableState`) must go red.

## Ladder

- **Tier 0** foundations: press/hover/focus-visible/keyboard modifiers, id+label association,
  FocusScope, Collection/Key/SelectionManager, overlay positioning, locale/direction.
  Gate: Button and ToggleButton pass both instruments on wasmJs; report generated by script;
  mutation check seen red.
- **Tier 1** simple widgets (20): Button, ToggleButton, ToggleButtonGroup, Checkbox,
  CheckboxGroup, RadioGroup, Switch, Link, TextField, SearchField, NumberField, ProgressBar,
  Meter, Separator, Group, Toolbar, Form, Disclosure, DisclosureGroup, Breadcrumbs.
- **Tier 2** collections + overlays (13): ListBox, Tabs, TagGroup, Menu, Popover, Tooltip,
  Modal, Select, ComboBox, Autocomplete, GridList, Slider, Toast.
- **Tier 3** heavy (21): Table, Tree, NavigationTree, Calendar family, Date/Time fields and
  pickers, Color family, DropZone, FileTrigger, Virtualizer, TokenField, PreviewTrigger.

"All 54" is the north star, not the promise. Tier 0 + Tier 1 + one Tier-2 component answers
the capabilities question.

## Running

```sh
source ~/.sdkman/bin/sdkman-init.sh
gradle :stately:jvmTest :stately:wasmJsTest              # state layer, both targets
gradle :aria:jvmTest                                     # inner loop, seconds
CHROME_BIN=$HOME/.cache/ms-playwright/chromium-1217/chrome-linux64/chrome \
  gradle :aria:wasmJsBrowserTest                         # truth run (Karma)
gradle :components:wasmJsBrowserDevelopmentRun -t        # dev server, continuous
gradle :components:wasmJsBrowserDistribution             # components/build/dist/wasmJs/productionExecutable/
cd conformance && npx playwright test                    # reference :5173 + dist :8081
node conformance/report.js > CONFORMANCE.md
```
